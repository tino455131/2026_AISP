Discord 團隊協作助手：系統流程圖

依目前 ping-voice-tmp 分支的程式碼，將系統分成 SQL、文字 Bot、語音 Bot、AI 四區。實線代表已有程式碼的路徑；灰色虛線卡片代表尚未接上的產品功能。這張圖描述程式流程，不代表已完成 Discord 實機驗收。

程式碼已有尚未接上最後核對：2026-11-21
總覽SQL文字 Bot語音 BotAI

四個系統如何連在一起

文字 Bot 與語音 Bot 蒐集資料；SQL 保存文字、逐字稿與摘要；AI 讀取逐字稿產生摘要。使用者要看保存內容時，讀取路徑會重新向 Discord 核對權限。

箭頭表示資料或呼叫方向。讀取 SQL 前的權限檢查、錄音同意條件與失敗路徑在下方各系統詳圖中展開。

1

SQL｜共同資料層

文字 Bot、語音轉寫與 AI 摘要都使用專案根目錄的 sqlite_api.py；單一 SQLiteStore 預設存取根目錄的 data/messages.sqlite3。對使用者讀取時，應經過授權 reader。API 用法與根目錄設定見 SQL API 文件與安裝說明。

資料寫入與保存
  1. 文字 Bot 呼叫 SQLiteStore依伺服器、頻道與訊息 ID 保存文字及匯入進度。sqlite_api.py
  2. 語音轉寫與 AI 呼叫同一介面保存一場錄音、逐字稿句子與會議摘要。sqlite_api.py
  3. 同一份 SQLite單一儲存模組建立資料表並設定 WAL，支援多個程式寫入。data/messages.sqlite3
  • messages
  • backfill_state
  • voice_sessions
  • voice_lines
  • voice_session_summaries
讀取邊界：SQLiteStore 的底層讀取方法本身不驗證 Discord 權限。面向使用者或 AI 的讀取請使用 AuthorizedMessageReader 或 AuthorizedTranscriptReader；內部轉寫與摘要流程可使用 store 處理資料。
2

文字 Bot｜Discord 訊息記憶

Python bot 只處理設定中的一個 Discord 伺服器。它能匯入可讀取的舊訊息，並記錄後續文字訊息與編輯、刪除事件。

寫入流程
  1. Discord 頻道文字頻道、語音／舞台頻道文字聊天、討論串。
  2. BotClient 事件啟動時 backfill_history；上線後 on_message 與編輯／刪除事件。bot.py
  3. SQLiteStore按穩定的 guild_id、channel_id、message_id 保存或刪除。sqlite_api.py
  4. SQL：messages只保存文字內容；無文字的附件不會存入。
授權讀取流程（提供後續 AI 使用）
  1. 指定讀取者與頻道呼叫時帶 member_id 與 channel_id，不以其他頻道權限替代。
  2. ChannelAccess向 Discord 查現在的 View Channel、Read Message History；私人討論串再核對成員資格。channel_access.py
  3. AuthorizedMessageReader確認通過才從同一頻道讀近期訊息；無法確認時拒絕。channel_access.py
  4. SQL：messages回傳該頻道的近期文字訊息。
目前 bot.py 對使用者公開的斜線指令只有 /ping；文字問答 /ask 在這個分支尚未接上。
3

語音 Bot｜同意錄音與轉文字

Node.js bot 管理 Discord 語音連線與使用者同意；Python voice_bot/voice_stt 在本機將同意者的錄音轉成逐字稿。

錄音與轉寫
  1. /record startRecordController 檢查組長身分，加入組長所在語音頻道並貼出同意按鈕。commands.js
  2. ConsentBook預設未同意；只錄已按「同意錄音」的人。撤回時刪除該次已錄片段。consent.js
  3. RecordingSession將同意者的發言存成 WAV 片段及 manifest。recorder.js
  4. /record stoprunIngest 呼叫 Python；沒錄到片段時不產生逐字稿。ingest.js
  5. voice_stt → SQLiteStore合併相近片段、以本機 Breeze-ASR-25 轉寫，再透過共用 API 保存。ingest_recording.py
  6. SQL：voice_sessions / voice_lines以會議、語音頻道與說話者保存逐字稿。
使用者查看逐字稿或摘要
  1. 查看按鈕點選「查看逐字稿」或「查看摘要」。commands.js
  2. show_session以按鈕使用者的 ID 發起讀取；透過 reader 查資料。show_session.py
  3. ChannelAccess + TranscriptReader按現在語音頻道的權限檢查；拒絕或無法確認都不提供內容。transcript_reader.py
  4. 僅點選者看得到Discord ephemeral 回覆，不把整份逐字稿或摘要公開貼到頻道。
錄音的 Discord 實際收音流程仍需測試伺服器驗收；本圖表示目前程式碼中的呼叫路徑。
4

AI｜會議摘要與未來協作功能

語音 Bot 在轉寫成功後呼叫 meeting_ai。摘要器可替換；目前預設是本機規則版 simple，另有需 API key 的 openai 版。

已寫入程式碼的會議整理流程
  1. SQL：voice_lines讀取單場會議逐字稿；不確定的句子標為 uncertain。
  2. summarize_session → SQLiteStore讀取 MeetingLine，呼叫可替換的 MeetingSummarizer，再將結果寫回共用 API。summarize_session.py
  3. simple 或 OpenAI產生摘要、決定與待辦草案，決定／待辦保留來源行號。interface.py
  4. SQL：voice_session_summaries保存內容、摘要器名稱、prompt 版本與來源句數；供查看按鈕讀取。
完整產品目標（目前尚未接上）
  1. 整合團隊進度結合文字紀錄與會議結果，找出需要處理的問題。
  2. 提出行動建議產生有來源依據的任務草案。
  3. 組長確認由組長審核與修改後才採用。
  4. 委派與協助執行交給對應成員的 AI agent，追蹤協作結果。
摘要工作是系統內部處理；把保存內容顯示給使用者時，仍須走授權 reader。目前沒有已接上的跨文字與語音資料 AI 問答、組長審核或任務委派入口。完整目標來自專案 README；AI 讀取保存內容的規則見 ai_memory_api.md。
